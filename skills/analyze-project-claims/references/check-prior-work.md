# Check prior work before reporting blockers or repeating tasks

Use this guide when resuming work, reporting progress or blockers, choosing the
next action, or requesting evidence, credentials, review or approval. It applies
to every participating agent and supplements existing evidence and authority
rules; it does not create a new approval step.

## Reconcile the smallest relevant scope

1. Read the existing evidence index and current structured claims or controller
   state. Follow applicable supersession links. A recent blocker paragraph is
   navigation, not a complete record of earlier achievements. If no index exists,
   use the project's existing artifact inventory; do not require a new catalog.
2. Open the relevant decisions, execution results and counterevidence. Match
   their source bindings, scope, configuration, generation or session, reviewer,
   decision, applicable expiry and consumed state to the proposed task. An
   omitted index entry calls for bounded lookup, not a missing-evidence claim.
3. Record a compact reconciliation in the existing task record:

   `item | completed/accepted scope | evidence | remaining delta | repeat decision and reason`

   Keep implementation, review, scientific acceptance, operational permission
   and observation freshness separate. Do not create another claims authority.
4. Reuse completed work and valid approvals within their scope. A narrower
   unresolved successor gate does not reopen a completed parent task. Age alone
   does not invalidate historical acceptance: identify an actual changed binding
   or applicable expiry. Conversely, historical acceptance does not grant a new
   session, broader use or fresh execution permission.
5. Before repeating work or asking again, identify the material changed input,
   new requirement, contradiction, applicable expiry, failed check or missing
   scope that warrants that repeat. Check existing user authorization first.
   Without a reason to repeat, retain the completed scope and work on the
   unresolved delta. Consumed attempts and one-shot approvals remain consumed.
6. Reconcile affected active claims and next actions before dependent execution
   or a completion claim. Preserve prior records and source snapshots as history;
   update the existing handoff, check table and index where present. Verify both
   evidence bindings and their meaning. A matching hash is not semantic proof.
   For read-only work, report the needed correction to the coordinator instead
   of modifying shared records.
7. Report completed scope first, then the exact remaining item and why earlier
   evidence does or does not cover it. Do not describe an entire capability as
   missing because one integration or freshness gate remains unresolved. Do not
   turn optional stronger analysis into a new execution prerequisite.

Use the lightest sufficient check. A bounded review of the relevant receipts is
not a request to reread all history, repeat passed tests, or reset a controller.
If lookup remains inconclusive within the authorized budget, state where you
looked and the unresolved applicability question; do not infer global absence.

## Decision walkthroughs

These synthetic examples illustrate intended choices, not executed behavioral
regressions or evidence that agents will reliably follow the procedure.

| Situation | Decision |
| --- | --- |
| An old note says review pending; a later source-bound decision approves the same scope with limits. | Preserve the approval and its limits; correct the old active pointer without requesting the review again. |
| A component identity is approved but performance for a new workload is untested. | Keep identity complete; investigate only the required performance delta. |
| Recorded data passes an integration check while a fresh session lacks its required receipt. | Preserve recorded integration evidence; identify the fresh-session input rather than calling the integration absent. |
| A service transition consumed exact approval; a separate ingestion gate is unresolved. | Do not restart the service or request the consumed operation again. |
| A source hash changes only in an index; the approved source snapshot remains intact. | Determine which claim depends on the changed bytes; preserve the historical snapshot rather than invalidating every approval or silently replacing its hash. |
| The same operation is now required on a different target, or an explicit grant expired. | Earlier success remains historical; check authority and prepare the exact new delta before execution. |
| An index omits a potentially relevant receipt. | Perform bounded lookup before declaring evidence missing or asking the user to supply it again. |

## Limits and reversal conditions

The guide is an agent procedure, not a runtime hook, automatic approval
validator or guarantee of compliance. Procedure presence and decision
walkthroughs do not establish improved agent behavior. Reopen a reuse decision
when material bindings, scope, counterevidence, authority or applicable freshness
requirements change, and retain the prior conclusion as history.

Use the project's existing controller and evidence protocol. No new execution,
publication, scheduler, resource or manual authority follows. Preserve journals,
selected executable bindings and cumulative budgets. The coordinator serializes
shared updates and retains the existing independent review requirements.
